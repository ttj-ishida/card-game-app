# ADR-0004: フレンド対戦のサーバー権威方式

- 状態: 承認
- 日付: 2026-09-04
- 決定責任者: プロジェクトオーナー
- TODO: M4-ARC-01
- 関連要件: SYNC-001～012, TX-001～004, INFO-001～009, NFR-S-001～005, REL-001～004

## 背景

M4では、2～6人のフレンド対戦を招待リンクから開始し、複数端末で同期・再接続しながら1局完走できる状態を目指す。

CPU戦では端末内の共有ルールパッケージが正となるが、オンライン対戦で同じ方式をそのまま使うと、手札の偽装、スキルの二重消費、同時送信による状態分岐、他プレイヤーの非公開情報漏洩を防ぎにくい。M4以降は、クライアントを表示と入力の担当に寄せ、対局状態の確定はサーバー側で行う。

既存方針として、環境はADR-0002の`local`、`development`、`staging`、`production`を使い分ける。M4のオンライン検証は`development`または`staging`で行い、`production`はM8まで作成しない。

## 入出力

### クライアントから送るもの

- `room_id`または`round_id`
- `actor_player_id`
- `expected_state_version`
- `request_id`
- 操作種別: ルーム作成、参加、退出、開始、カード提出、パス、スキル使用、再接続、CPU引継ぎ
- 操作に必要な最小限の入力: 選択カードID、選択スキルID、変化先、宣言値など

クライアントは、他プレイヤーの手札、未公開スキル、山札順、サーバー内部乱数を送らない。

### サーバーから返すもの

- 受理または拒否
- 最新の`state_version`
- 公開状態のスナップショット
- 操作者本人だけが読める手札・スキル差分
- 表示用イベント
- 拒否時の理由コード: `not_your_turn`, `stale_state`, `illegal_move`, `already_processed`, `room_closed`, `not_a_member`

## 選択肢

| 選択肢 | 開発工数 | 運用費 | セキュリティ | 将来拡張 | 利用者体験 |
| --- | --- | --- | --- | --- | --- |
| A. クライアント権威 + Realtime同期 | 低 | 低 | 低。手札偽装と二重操作を防ぎにくい | 低。公式対戦へ伸ばしにくい | 実装初期は軽いが、端末差分で壊れやすい |
| B. Edge Function + 共有TSルール + 条件付きDB更新 | 中 | 中 | 高。サーバーで操作を検証できる | 高。M5の公式対戦へ拡張しやすい | 同期失敗を再試行・再接続で吸収しやすい |
| C. Postgres関数中心のサーバー権威 | 中～高 | 低～中 | 高 | 中。TSルールとDB実装が二重化しやすい | DB内で原子的だが、ルール変更の速度が落ちる |
| D. 専用ゲームサーバー | 高 | 高 | 高 | 高 | 低遅延を狙えるが、M4の範囲には重い |

## 決定

選択肢Bを採用する。

M4のフレンド対戦では、Supabase Edge Functionをプレイ要求の入口にし、共有TypeScriptルールパッケージで合法手を検証する。対局状態はPostgresの`state_version`を持つ行として管理し、`expected_state_version`が一致した場合だけ1つのDBトランザクションで更新する。

同じ`request_id`の再送は冪等に扱い、初回と同じ結果を返す。これにより、通信タイムアウト後にユーザーが再送してもカードやスキルが二重に消費されない。

## 後続TODOへの前提

- M4-ARC-02: 共有ルールパッケージはExpoとEdge Functionの両方から参照できる境界へ整理する。ルールの正本は1つにする。
- M4-SB-01: `rooms`、`room_players`、`rounds`、`round_players`は、ルーム状態、参加者、対局状態、席順を分けて保持する。
- M4-SB-02: `round_hands`と`round_skills`は所有者単位で分離し、RLSで本人またはサーバーだけが読める。
- M4-SB-03: `round_public_state`は全参加者に公開できる状態だけを持つ。`round_events`は表示・監査・再接続のための追記ログにする。
- M4-SB-06～08: プレイ要求はEdge Functionで受け、`expected_state_version`と`request_id`を必須にする。
- M4-SB-09～10: Realtimeは通知路として使い、取りこぼしや順序ずれがあった場合は最新スナップショット取得で復旧する。
- M4-SB-12: 退出、棄権、CPU引継ぎもサーバー権威の状態遷移として扱う。

## 失敗系

- `expected_state_version`が古い場合、サーバーは更新せず`stale_state`と最新版を返す。
- 合法でないカード提出、手番外操作、所有していないスキル使用は更新せず拒否する。
- Edge Functionの処理途中で失敗した場合、DBトランザクションをロールバックし、部分更新を残さない。
- Realtimeイベントの欠落、順序入替、重複はクライアント側で`state_version`とイベント連番により検知し、スナップショット再取得へ切り替える。
- 非公開情報は公開状態とイベントへ含めない。本人の手札・スキルは所有者別テーブル経由で読む。

## 不採用理由

- クライアント権威方式は、M4のフレンド対戦だけなら短期実装できるが、手札偽装、スキル二重消費、端末間の自然革命・場流れ分岐を根本的に防げないため不採用とする。
- Postgres関数中心方式は原子的更新に強いが、既存のTypeScriptルールエンジンとPL/pgSQL側のルールが二重化し、カード追加・スキル追加時の保守負荷が高いため不採用とする。
- 専用ゲームサーバーは、公式対戦や低遅延要件が強くなった段階では候補になるが、M4の個人開発範囲では運用費と実装量が大きいため不採用とする。

## 見直し条件

次のいずれかが発生した場合、このADRをSuperseded候補として再検討する。

- Edge Functionの実行時間、同時接続、デプロイ制約がM4-QA-03の50局連続対戦を満たせない。
- Realtimeとスナップショット再取得だけでは、60秒再接続の利用者体験が成立しない。
- M5の公式対戦で、不正監査、ランキング、時間切れ処理に専用サーバーが必要になる。
- 共有TSルールをEdge Functionへ持ち込むビルド構成が保守不能になる。

## 検証方針

- M4-SB-06で、合法手、違法手、手番外操作、古い`state_version`、同一`request_id`再送を自動テストする。
- M4-SB-07で、1つのDBトランザクション内に公開状態、本人手札、スキル、イベントの更新が収まることを確認する。
- M4-SB-09で、Realtimeイベントの重複・順序入替・欠落を検出し、スナップショット再取得へ戻れることを確認する。
- M4-QA-01～03で、2～6クライアントの自動操作と50局連続対戦を通す。
